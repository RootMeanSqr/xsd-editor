# XML Schema Definition (XSD) Graphical Editor Requirements Specification

This document details the functional, non-functional, and design requirements for the platform-independent XSD Graphical Editor.

**Requirement identifiers.** Each requirement carries a stable identifier, `XE-nnn`, assigned once. An identifier belongs to the requirement, not to its position: it never changes when sections are reordered or renumbered, and it is **never reused** — a requirement that is removed takes its identifier out of circulation with it. New requirements take the next unused number regardless of where they are inserted, so the sequence is not in document order and is not meant to be read as one. Cite identifiers from outside this document — tests, commit messages, issues — where a section number would go stale. Cross-references *within* the document keep the readable section-and-label form.

**Reference corpus.** Requirements are validated against a reference schema set comprising a primary message-definitions file plus two smaller companion schemas. Where a requirement carries a numeric threshold, the corpus figure that justifies it is cited inline.

## 1. Scope & Style Focus

- **`XE-001`** · **Delivery Strategy**: **Reference corpus first, general later.** Release 1 targets the reference corpus and derives its scope from it. Later releases broaden to general Venetian Blind XSD editing. Exclusions below are therefore split into two categories — deferred and permanent — and a deferred exclusion must not be designed out of the architecture.
- **`XE-002`** · **Intended User**: A **schema author who knows XSD**. The graphical view exists to make a large schema navigable and editable at speed, not to hide XSD from someone unfamiliar with it: Text View is a first-class surface rather than a fallback, and anything outside R1 scope is edited there directly. This is what justifies the posture the rest of the document takes — the editor reports rather than prevents (§2.1), leaves Venetian Blind conformance to the author (below), and accepts references to types that do not exist yet (§2.2). Where a later decision could go either way, it should favour an author who knows what they intend over one who needs to be guided to it.
- **`XE-003`** · **Style Focus**: The editor is optimised for the **Venetian Blind** style of XSD construction — globally defined complex and simple types, with global elements referencing those types, keeping nesting clean and reusable. The reference corpus is pure Venetian Blind: roughly 5,500 named types and **zero anonymous type definitions**. The zero is exact and load-bearing; the type count is a magnitude.
- **`XE-004`** · **XSD Version**: **XSD 1.0 only**, in R1 and beyond. XSD 1.1 constructs (`xs:assert`, `xs:alternative`, open content) are permanently out of scope.
- **`XE-005`** · **Supported constructs (R1)**:
  - Global Elements (messages) — roughly 700 in the corpus
  - Globally named ComplexTypes — roughly 4,600
  - Globally named SimpleTypes — roughly 900
  - `xs:sequence` and `xs:choice` model groups
  - `xs:complexContent` / `xs:extension` derivation
  - `xs:restriction` with facets
  - `<xs:include>` and `<xs:import>` directives
  - **Anonymous (inline) complexTypes**, as a transient authoring state only — see Venetian Blind Conformance below
- **`XE-006`** · **Venetian Blind Conformance**: The finished schema is expected to contain **no anonymous type definitions**. This is a property of the completed artifact, not of the editing session, and it is **an authoring convention the editor does not enforce**. The editor neither blocks nor warns on save, and remaining anonymous types are not reported as validation entries; ensuring the schema is fully promoted is the author's responsibility. The editor explicitly supports sketching structure inline — nested elements, sequences, and choices under an element — and then promoting that structure to a globally named type via Extract Global ComplexType (§2.3). Anonymous types are therefore a supported intermediate state that the editor must create, render, and edit.
- **`XE-007`** · **Deferred features**: **exporting the Design View canvas as an image is R2.** The canvas is viewable only inside the editor in R1, so schema structure cannot be shared as a picture; this is accepted for R1 and scheduled rather than left open.
- **`XE-008`** · **Future features**: wanted, but not scheduled to a release. Listed so the answer is on record and the architecture does not preclude them, without implying a date.
  - **Licence or activation checking** — any scheme requiring the application to contact a server to confirm entitlement. It would breach **No Network Egress** (§5), so it is recorded here rather than assumed available should the product ever be licensed that way.
  - **Instance-document validation** — validating an XML instance against the open schema. Excluded from R1. It is the question a schema exists to answer, so it is not a permanent exclusion, but it is a larger change than it appears: it introduces a second document kind, with its own opening, tab, and editing model, and an error surface that maps instance positions back to schema constructs. Every part of this specification — the object model, both views, all four panels, every editing path — assumes the open document is a schema. **Create Schema Subset** (§2.1) is its natural companion, since the subset file is what a consumer would validate against.
- **`XE-009`** · **Deferred constructs**: `xs:attribute` declarations and attribute groups; `xs:group`; `xs:union`; `xs:list`; `xs:simpleContent`; mixed content; the element-level `default` and `fixed` attributes; and the additional defaulted attributes `nillable`, `form`, `block`, and `final` (§2.4). These are absent from the reference corpus but common in general Venetian Blind schemas. They are excluded from R1 scope only.
  - `default` and `fixed` on element declarations are excluded on the same terms: the reference standard permits neither, so R1 offers no path to display or edit them. Where a general schema carries them they are preserved verbatim like any other unsupported construct (§1, Round-trip safety) and remain editable in Text View. Should they later come into scope, the Details Pane (§2.4) must enforce that the two are mutually exclusive on one element, and that `default` is meaningful only where `minOccurs` is 0. The document model, Details Pane, and serialiser must accommodate them without structural rework.
- **`XE-010`** · **Product non-goals**: schema generation from instance documents, code generation, schema diffing, documentation generation, and version control integration. The editor edits schemas; these are separate tools.
- **`XE-011`** · **Permanently out of scope**: `substitutionGroup`, `xs:key` / `xs:unique` / `xs:keyref`, `xs:redefine`, and `xs:override`. These conflict with the Venetian Blind style focus rather than merely being unused.
- **`XE-012`** · **Round-trip safety**: Files containing deferred or out-of-scope constructs must open, save without corruption, and remain fully editable in Text View, even where Design View cannot render them. This applies from R1, since general schemas will be opened before general editing is supported. Unsupported constructs render as placeholders per §2.2.

## 2. Core Functional Requirements

### 2.1 Workspace & File Management

- **`XE-013`** · **Platform Independence**: The application must run identically on Windows, macOS, and Linux. It is a desktop application, packaged per §5, Delivery Form.
- **`XE-014`** · **Multi-File Handling**: Support opening, editing, and saving multiple XSD files concurrently using a tabbed layout.
- **`XE-015`** · **File Creation**: Support creating a new, empty XSD file with a user-specified target namespace.
- **`XE-016`** · **Directive Resolution**: Read and resolve `<xs:include>` and `<xs:import>` references so that validation, type resolution, and the type picker (§2.2) operate across the full set of referenced files, not just the active file.
  - **Text View has no autocompletion.** It is a plain XML editing surface — syntax highlighting, folding, search, and validation markers (§2.2), and nothing that completes a name as the user types. Completion belongs to the structured surfaces, where the editor knows what kind of name is wanted; in free text it would have to guess. A type name typed wrongly there is caught by the reference check below rather than prevented at the keystroke.
- **`XE-017`** · **Built-in Types Always Resolve**: The XSD built-in datatypes — `xs:string`, `xs:double`, `xs:dateTime`, `xs:ID` and the rest of the 1.0 set, primitive and derived alike — resolve implicitly, in every file, with no `xs:import` or `xs:include` required. They belong to the XML Schema namespace, which a schema is never obliged to import, so a reference to one is never an unresolved reference and never produces a red squiggle or a Bottom Pane entry.
  - They are part of the **resolved closure** for every purpose that closure serves: the type picker offers them (§2.2), validation accepts them (§3), and pasting an element typed by one into another file (§2.3) brings no dependency with it and leaves nothing unresolved.
  - What must still be present is the ordinary **namespace binding**: the reference names a prefix, and that prefix has to be bound to `http://www.w3.org/2001/XMLSchema` in the file. A qualified name whose prefix is not bound to anything is a namespace error (§3), which is a different failure from a type that cannot be found and is reported as such. The conventional `xs` binding is not required — a file binding the schema namespace to some other prefix resolves identically.
  - Built-ins are not workspace objects: they are not listed in the Left Panel object tree (§2.4), are not renamable or deletable (§2.3), and have no definition to navigate to. Expanding an element typed by one renders the terminating node of a derivation chain, per §2.2.2.
- **`XE-018`** · **Location Resolution**: R1 resolves two `schemaLocation` forms — **relative paths** and **absolute local paths**.
  - Relative paths resolve against the directory of the **referencing file**, not the active document or the process working directory. In a chain where A includes B and B includes C by relative path, C resolves relative to B.
  - XML catalogs and network URLs (`http:`, `https:`) are **not supported in R1**. A directive using an unsupported form is reported distinctly from a file that is simply missing, so the user can tell "this editor cannot fetch that" from "that file is not there".
  - Absolute paths are inherently platform-specific and may not resolve when a schema authored on one operating system is opened on another (§2.1, Platform Independence). Such a failure is reported as an unresolvable directive rather than treated as a defect.
  - `schemaLocation` values are never rewritten on save, including when a directive could not be resolved.
- **`XE-019`** · **Unresolvable Directives**: A file whose `include` or `import` targets cannot be resolved **still opens and remains fully editable**. The editor degrades rather than refusing.
  - The unresolvable directive is flagged in place, in both Text and Design Views, and reported in the Bottom Pane.
  - Type references that cannot be resolved because of the missing file render as **unresolved placeholders**, marked with a **red squiggly underline** on the reference text in both Text View and on the Design View element card. The reference is displayed, cannot be expanded, and the referencing element remains editable. Hovering or selecting the marked reference reports the reason and the missing file.
  - The red squiggly underline is the general marker for unresolved and invalid references, applied consistently wherever such a reference appears rather than only at the directive site. The squiggle's waveform carries the meaning independently of its colour, satisfying §5's requirement that information not depend on colour alone; the specific red must still meet contrast in both Light and Dark themes.
  - The unresolvable directive and all references depending on it are preserved verbatim on save. A missing file never causes its references to be rewritten or dropped.
  - If the missing file later becomes available, resolution is re-attempted on the next validation pass (§3) without requiring the document to be reopened.
- **`XE-020`** · **Namespace Handling**: Namespace declarations and prefixes are **modifiable**, not merely preserved. The editor reads and resolves them, and supports restructuring them from the Details Pane.
  - The **target namespace** may be set at file creation (§2.1, File Creation) and changed at any time thereafter.
  - Prefixes may be **declared, renamed, and removed**. Renaming a prefix rewrites every qualified name bound to it within the file, in the same single operation and single undo entry as a type rename (§2.3).
  - Prefix conflicts across imported schemas are reported and resolvable by rebinding one of the conflicting prefixes.
  - **Cross-file consequences follow the rename policy (§2.3).** A prefix binding is local to its file, so renaming one affects nothing else. Changing a file's target namespace does affect every file that imports it: the editor warns, names the referencing files, and reports the count, but does **not** rewrite them.
  - A prefix that is declared but unused is preserved on save rather than removed. The editor does not tidy namespace declarations it did not touch.
  - Prefix restructuring also remains available in Text View, since that view is unrestricted.
- **`XE-021`** · **Create Schema Subset**: Produces a new XSD file containing a chosen set of top-level elements and everything they depend on. A message-set schema is large — roughly 700 global elements over some 5,500 types in the reference corpus — and a consumer usually needs a handful of messages, not the whole standard. This is the feature that gets them that file.
  - **Selection window**: a scrollable, multi-select list of **every top-level element** in the resolved `include`/`import` closure (§2.1), with the same wildcard filter as the Left Panel object tree (§2.4) and the same virtualisation requirement (§5). Selecting nothing leaves the action disabled; there is no implicit "all".
  - **Include abstract type extensions** — a checkbox on the window. When set, every type in the subset that is `abstract` also brings in **all types derived from it, transitively**: the derivations of those types, and so on. Those added types bring their own dependencies with them, which may pull in further abstract types, so the rule is applied to a fixed point rather than a single pass. The corpus holds about 70 abstract types.
    - Left unset, an abstract type is written with no concrete implementations, and a document instance would have nothing to substitute for it. The checkbox is the difference between a subset that describes the messages and one that can carry them, so it is presented as a plain choice rather than buried in preferences.
  - **The dependency closure** is the transitive one: each selected element's type, that type's base type, the types of its child elements, the base types of those, and so on down to the built-in datatypes (§2.1, Built-in Types Always Resolve), which are never copied because they never need to be.
  - **Execution** prompts for a destination filename, defaulting to the directory of the active file, and confirms before overwriting an existing file. The subset is then written, and **the new file is opened in a new tab** when it completes.
  - **What the written file contains**: the selected elements and the closed set of types, each copied **verbatim** — annotations, comments, and character references preserved on the same terms as an ordinary save (§4), and attributes serialised in the configured order (§4, Attribute Ordering). Only the namespace prefix declarations the subset actually uses are carried over.
    - The file carries the **target namespace of the schema the elements came from**. A dependency belonging to a *different* target namespace cannot be inlined into it, so it is left as an `xs:import` with its original `schemaLocation`, and the operation reports which dependencies were handled that way. A subset drawn from a single target namespace — the corpus case — is fully self-contained.
    - The result is a **new file, not a new state of an existing one**. The source documents are not modified, no tab becomes dirty, and the operation creates no undo entry (§2.3): there is nothing in the open documents to undo.
  - On completion the editor reports how many elements and types were written, so a subset that came out far larger than expected is visible immediately rather than after opening it.
- **`XE-022`** · **Unused Types Report**: An on-demand report listing the **global types that nothing can use**, run from the Tools menu (§2.4) and written to the Bottom Pane (§2.4) like any other list of findings. On a corpus of several thousand types, definitions outlive the references that once pointed at them, and nothing else in the editor surfaces that.
  - **Reachability is computed from the global elements**, not from reference counts. A type is **used** if it is reachable by walking outward from any top-level element in the resolved closure (§2.1) — the element's type, that type's base, the types of its children, and so on. Counting references alone would be wrong in the opposite direction as well: it would report every top-level element's own type as unused, since nothing references a message.
  - **A type derived from a used type is itself used.** Where a concrete type extends a reachable base, it stays out of the report even if no element names it directly: an instance document may carry it in place of the base, so the definition is doing real work. Derivation propagates reachability transitively, so a chain of extensions from a used base is used along its whole length. This is the same relationship **Create Schema Subset** (§2.1) follows when **Include abstract type extensions** is set, applied here to decide what counts as used rather than what to copy.
  - **Only types are reported** — ComplexTypes and SimpleTypes. Global elements are the roots of the walk and are never reported, whether or not anything references them.
  - The report **finds nothing to act on by itself**: an unused type is valid XSD, not an error, so entries carry no validation severity and no inline markers appear. Double-clicking an entry navigates to the type per **Navigating to an Object** (§2.4), and removing it, if that is what the user wants, is an ordinary **Delete** (§2.3).
  - It is run on demand and not as part of a validation pass (§3). The walk is a whole-closure computation, and attaching it to a pass that already runs on every file load and save would add cost to the common path for a finding that is rarely urgent.
- **`XE-023`** · **Save Model**:
  - Explicit save only. **No autosave and no crash-recovery journal** — both are deliberate v1 non-goals.
  - Each tab displays a dirty-state marker whenever it holds unsaved changes.
  - Closing a dirty tab, or quitting with any dirty tab open, prompts the user to save, discard, or cancel.
- **`XE-024`** · **External Change Detection**: If a file open in the editor is modified on disk by another process, the editor prompts the user to either reload from disk or keep the in-editor version.

### 2.2 Dual-View Editing Mode

- **`XE-025`** · **Single-Pane View Switching**: The main window switches between **Text View** and **Design View** via a toggle control on the Top Ribbon (§2.4). Only one view is rendered at a time, maximising screen space.
  - The view mode is a property of the **window, not the tab**. Switching tabs, or landing in a tab opened by a cross-file navigation (§2.4, Navigating to an Object), shows the same view the user was already in. A per-tab view mode would make the active view change under the user as they move between files.
- **`XE-026`** · **Text View**:
  - Full text/XML representation of the active XSD file.
  - **Monospaced font.** Text View renders in a fixed-width face, so that indentation, attribute alignment, and column positions read as a grid. Design View instead uses a proportional face chosen for reading, since a canvas of names and annotation prose gains nothing from fixed pitch and loses width to it.
    - **Both defaults are the platform's own fonts** — the native monospaced face for Text View and the native UI face for Design View, resolved per operating system rather than named as one font that exists on only one of them. Nothing is fetched at runtime (§5, No Network Egress): a face is either installed on the system or the platform's own fallback applies. The user may select a different installed face for either view.
    - Because the two views use different families, they take **separate size settings** (§2.4, Preferences) rather than sharing one. A proportional face sets shorter than a monospaced one at the same point size, so a single control would leave one view or the other wrong.
  - Syntax highlighting, line folding, search-and-replace, and inline validation markers.
  - **Syntax Highlighting**: XML syntax is coloured by token class — element names, attribute names, attribute values, text content, comments, character and entity references, CDATA, and the XML declaration — with XSD-namespace element names distinguished from foreign-namespace ones, so `ext:` extensions read differently from schema constructs.
    - Highlighting is **lexical, not semantic**. It reflects the token the parser sees, never whether a type reference resolves; resolution is carried by the validation markers (§3) instead, which is what keeps highlighting working while the buffer is malformed.
    - It therefore **continues to work on a non-well-formed buffer** (§2.2, Malformed Buffer Handling), degrading to plain text only from the point where the lexer can no longer proceed.
    - Token colours are theme-aware and meet the §5 contrast requirement in both Light and Dark, and no token class is distinguished by colour alone where the distinction carries meaning.
- **`XE-027`** · **Design View**:
  - A canvas-based node-graph representation of the XSD structure.
  - **Canvas Root**: The canvas renders a single object — an Element, ComplexType, or SimpleType — as its visual root, focused and centred. Until the user first navigates, the canvas is empty.
  - **Re-rooting**: The root changes only by explicit navigation, and six paths perform it: an entry in the Left Panel object tree (§2.4); a Bottom Pane validation entry (§2.4); an entry in the Dependencies Tree (§2.4); Undo/Redo Navigation (§2.3); creating a global object from the canvas (§2.3, Create Global Object); and a **double-click on the `Base Type` row in a ComplexType box header** (§2.2.1). The six are equivalent. No panel owns the root, and none is privileged over the others.
    - The three panel paths re-root **when Design View is active**. With Text View active the same double-click jumps to the object's declaration in the text instead (§2.4, Navigating to an Object); the canvas root is untouched and is what it was when Design View is next shown. The other three paths originate in Design View and therefore always re-root.
    - The base type row is the **only** canvas label that re-roots. Double-clicking an element card's `Type` row edits the type instead (see **Changing an Element's Type** below); no other type name on the canvas navigates.
    - A base type carrying an unresolved reference (§2.1) cannot be re-rooted to. The attempt reports the missing file and leaves the canvas as it stands, rather than clearing it.
  - **Selection Does Not Re-root**: A single click on a node inside the canvas selects it, highlights it with a thick outline, and loads its properties into the Details Pane, without changing the root. Single-click inspects, double-click navigates. This distinction — not ownership of the root by one panel — is what prevents unintended re-rooting during canvas interaction.
  - **The Object Tree Does Not Latch**: The Left Panel (§2.4) is a filterable listing of the file's objects, not a selection model. It holds no persistent selection, marks no current item, and is unaffected by re-rooting performed from any other path. Clicking an entry navigates the canvas; that is its only role.
    - Because no panel now indicates the current root, **the canvas must display it itself** — the root object's name and kind, shown persistently and independently of pan and zoom position. With no latched sidebar entry there is otherwise nothing that answers "what am I looking at" once the user has panned away from the root node.
  - **Changing an Element's Type**: Double-clicking the `Type | <typeName>` row on an element card opens a type picker and, on confirmation, rewrites the element's `type` attribute to the chosen type.
    - The picker offers the named ComplexTypes and SimpleTypes available in the resolved `include`/`import` closure (§2.1), together with the built-in datatypes, which are always available (§2.1, Built-in Types Always Resolve). It must be filterable rather than a plain list: the corpus offers some 5,500 named types.
    - **It completes as the user types.** Each keystroke narrows the list to the type names **beginning with** what has been typed, matched **case-insensitively**. Prefix matching is what suits these names — a corpus of long, systematically prefixed identifiers, where a substring match would return most of the list for a short input.
    - This picker, and the equivalent field in the Details Pane (§2.4), are the **only** places the editor completes a type name. Text View does not (§2.1, Directive Resolution).
    - **A name outside the closure is accepted.** The user may type a type that does not yet exist — an author often knows what they intend to create or import next — and the resulting reference renders as unresolved per §2.1, with the red squiggly underline and a Bottom Pane entry, until the type appears. This follows the same degrade-rather-than-refuse posture as an unresolvable directive: the editor reports the gap, it does not prevent it.
    - **Design View refreshes on confirmation.** The element's subtree is re-rendered against the new type, following that type's own expansion markers (§2.2, Expansion State). Nothing is discarded — the previous type's markers survive, since they belong to that type and not to this element — and the canvas root is unaffected.
    - Where the element's previous type was an inline anonymous complexType (§1), assigning a named type removes that inline definition. The change is one semantic operation and therefore one undo entry (§2.3), which restores the inline structure.
  - **Nested Bounding-Box Enclosers**: ComplexTypes render as enclosing bounding boxes. All child elements and nested structures are positioned **inside the bounds of their parent type box**. Expanding a nested element renders its referenced ComplexType as a nested encloser box, recursively, to unbounded depth.
  - **Joint Circle Connectors & Right-Angled Branching**: Model groups are represented on connection lines by a small circular joint node. The stem from the parent leads into the joint circle, which splits into right-angled branch connectors linking to each child card. Joint circles, stems, branches, and child cards must remain exactly middle-aligned under all sizing changes and nested expansions.
    - **Glyphs**: Sequence and choice are distinguished by pictorial icons rather than letters, following the convention established by existing XSD design tools. Sequence and choice must be distinguishable by icon shape alone, without relying on colour or on a text label.
    - Because the glyphs are not self-explanatory, the joint node exposes its model group kind on hover or selection, and the context menu that converts between sequence and choice (§2.3) names the current kind explicitly.
  - **Element Card Layout**: Each element card shows the element name on an upper row and a `Type | <typeName>` row beneath it.
  - **Cardinality Annotation**: An occurrence-range label (`0..∞`, `0..17`, `1..4`, `2..2`) is displayed to the left of an element card **only where the element can occur more than once** — that is, wherever the effective upper or lower bound exceeds `1`. The label is suppressed for `1..1` and for `0..1`.
    - **Optionality is carried graphically, not by the label** (`XE-082`). `0..1` therefore needs no label: the dashed outline and dashed connector already say it, and labelling it as well would put text beside a large share of the cards in a schema that is mostly optional single elements, for a distinction the line style has already made.
    - Where the label *is* shown, it states the **whole effective range**, including a lower bound of `0` — `0..∞` is written in full, not as `..∞`. The dashed rendering and the label then agree rather than splitting one fact across two places.
    - Repetition has no graphical encoding of its own, which is why it keeps the label. An author scanning for repeating structure is looking for the numbers.
  - **Universal Expansion Control**: **Every** element card displays an expand/collapse control, regardless of whether its type is a ComplexType, a named SimpleType, or a built-in primitive. What expansion renders is defined in §2.2.1 and §2.2.2.
  - **Expansion State**: Expanded/collapsed is a property of the **object**, held per tab, not a property of a position on the canvas. Each tab keeps a marker for every object it has rendered; the schema file is never written to record it, and the state does not outlive the tab.
    - Because the marker belongs to the object, it is **shared by every occurrence of that object**. Expanding a type while traversing one branch means that type is expanded wherever else it appears, and remains expanded when the canvas is re-rooted onto it. This is what makes Back and Forward (§2.2, Navigation History) return the user to the structure they left rather than to a collapsed root.
    - An occurrence renders expanded only if its own marker is expanded **and** every ancestor between it and the current root is also expanded. A collapsed parent hides its subtree regardless of the markers within it.
    - An object never touched by the user defaults to collapsed.
    - An inline anonymous complexType (§1) has no identity to share, so its marker is keyed to the element that owns it.
    - **Re-rooting always expands the root, in the render only.** Re-rooting onto a type shows the immediate child elements of that type and of its base type (§2.2.1), whatever the stored markers say. The override establishes what the user sees on arrival and is **never written to the markers**. Writing it would mean that merely visiting a type marked it expanded, and since markers are shared across occurrences, browsing types one at a time would progressively mark the whole schema expanded until every view opened fully expanded. Deeper levels follow their own markers.
    - **Only an explicit expand/collapse writes a marker.** Clicking the control on a card records the new state for that object. Navigation never does — not re-rooting, not Back or Forward (§2.2, Navigation History), not a Bottom Pane or Dependencies Tree entry. Collapsing a root that arrived expanded by the override supersedes it for the current render and records that object as collapsed.
    - **Recursion bound**: before expanding an element, the renderer compares its type against the types already present in that element's **ancestry within the current render** — the chain of enclosing type boxes from the displayed root down to its parent, base-type boxes (§2.2.1) included. If the type is already in that chain, expansion stops there.
      - The stopped element renders with a **`…` indicator** in place of its expanded content, showing that structure continues but repeats. Hovering or selecting it names the repeating type and where in the ancestry it occurs.
      - The bound is on the render, not the marker. The type keeps whatever expansion marker it has, and expands normally wherever it occurs outside its own ancestry.
      - The check is against the ancestry rather than the type alone, so it also catches mutual recursion (`A` containing `B` containing `A`), and so a type that merely appears twice in unrelated branches is unaffected.
      - Without this bound, per-object expansion state would expand a recursive type without limit: its marker being expanded would apply to the occurrence inside itself, and to that occurrence's own inner occurrence, indefinitely.
  - **Anonymous Type Rendering**: An element whose type is an inline anonymous complexType renders its content as a nested bounding box in the normal way, but with no type name in the box header and no `Type` row on the element card. The box carries a visual marker distinguishing it from a named global type. Because conformance is unenforced (§1), this marker is the **only** signal that structure remains to be promoted, so it must be readily noticeable at normal zoom rather than a subtle styling difference.
  - **Unsupported Construct Rendering**: Constructs outside R1 scope (§1) — whether deferred or permanently excluded — render as **opaque placeholder nodes** in Design View, positioned in document order where the construct occurs.
    - The placeholder names the construct (e.g. `xs:group`, `xs:union`) and any identifying attribute, so the user knows what occupies that position without switching to Text View.
    - Placeholders are read-only on the canvas. The construct remains fully editable in Text View and is preserved verbatim on save (§1, Round-trip safety).
    - **A placeholder is not an error state and must not be styled as one.** Design View now has three distinct "cannot display this" conditions that carry different meanings and must be visually distinguishable: an unsupported-construct placeholder (valid schema, outside editor scope); an unresolved reference (§2.1, red squiggly underline, genuine error); and a gap marker (§2.2, unparsed region of a malformed buffer). Only the second indicates something wrong with the schema.
  - **Abstract Type Indication**: Types declared `abstract="true"` render with a distinguishing badge or italic label on the type box. About 70 such types exist in the corpus.
  - **Annotation Rendering**: Where **Show Annotations** is on (§2.4, Top Ribbon), `xs:annotation` / `xs:documentation` text renders inline on element cards and type boxes.
    - **Only the first annotation is rendered.** A single element or type may carry several `xs:annotation` children — the top-level elements of the reference schema do — and the canvas shows the first in document order only. Where more exist, the object carries an indicator giving the count, and all of them are reachable through **Edit Annotations** (§2.3).
    - **Height is bounded by a user-configurable row limit** (§2.4, Preferences). Text beyond the limit is clipped with an ellipsis on the final row. The limit applies per object, so one heavily documented type cannot dominate the canvas.
    - **Width is bounded by the object that carries it.** Annotation text wraps within the element card's or type box's existing width and never widens it. Box width is set by the name, type, and structure; annotation text is a passenger of that width, not a driver of it, so turning annotations on never reflows the graph horizontally.
    - The full text of a truncated annotation is available on hover and in the Details Pane (§2.4). Truncation is a display bound only — nothing is altered in the document, which is preserved verbatim on save (§4).
  - Support visual editing of element names, types, and annotations.
- **`XE-028`** · **Navigation History**: The editor maintains a **back/forward history of navigation**, spanning both views, reached from the Top Ribbon (§2.4) and platform-conventional keyboard shortcuts.
  - Scope is **per tab**, matching Undo/Redo (§2.3). Each open file carries its own history.
  - The history is **unified across views**, in the same way the undo stack is. An entry records a location and the view it was in — a canvas root in Design View, a position in Text View. Moving back or forward to an entry belonging to the other view switches to that view, so the user is never returned to a location they cannot see. Where consecutive entries share a view, no switch occurs.
  - Design View entries are pushed by all six re-rooting paths (§2.2, Re-rooting).
  - Text View entries are pushed by **discrete jumps only** — a navigation from any of the three panels while Text View is active (§2.4, Navigating to an Object), a search or find-and-replace result, a go-to-line, and the landing position when a view switch or a history move arrives in Text View. Ordinary scrolling, caret movement, and typing do not push entries; a history that recorded them would be unusable.
  - **Navigation history is not Undo/Redo.** It moves the user without changing the document, and Undo/Redo changes the document without being reachable from it. They are separate stacks with separate controls. Where they touch: an undo or redo that relocates the user (§2.3, Undo/Redo Navigation) pushes a navigation entry like any other move, so Back returns to where the user was before the undo — while the edit itself is reversed only by Redo.
  - Forward entries are discarded when the user navigates somewhere new after going back, per normal convention.
- **`XE-029`** · **Go to Definition**: Jumps from a reference to the declaration of the type it names. Available in **both views**, by **`Ctrl` + click** on the name (the platform-conventional modifier) and from **Go to Definition** on the context menu.
  - **Text View**: the qualified name under the pointer, inside a `type`, `base`, or `ref` attribute value. Elsewhere in the text the action is not offered.
    - **Double-click in Text View selects a word**, as in any text editor. It does not navigate. The double-click-navigates rule belongs to the canvas and the panels (§2.4), where a row stands for an object; in a text buffer, word selection is what the gesture means and overloading it would cost the user an ordinary editing action.
  - **Design View**: the type name on an element card or in a type box header, and the same action on the context menu of either. This is the general form of the `Base Type` row double-click (§2.2.1), which remains as the quicker path on that row.
  - **The jump stays in the view it started in.** Invoked in Text View it scrolls to the type's declaration in the text and briefly highlights it; invoked in Design View it re-roots the canvas on that type. Go to Definition never switches views — it is a jump within the surface the user is working in, not a change of surface.
  - The landing otherwise follows **Navigating to an Object** (§2.4): the highlight duration is the same preference, a declaration in an `include`d or `import`ed file opens that file silently, and the jump pushes a Navigation History entry (§2.2).
  - **A name that resolves to nothing cannot be jumped to.** The action reports that the type is not defined and leaves the view as it stands, matching the unresolved base type rule (§2.2, Re-rooting). The same applies to a **built-in datatype**, which has no declaration anywhere to navigate to (§2.1, Built-in Types Always Resolve); the action is offered but reports rather than failing silently.
- **`XE-030`** · **Immediate Synchronisation**: Changes in Design View are written to the in-memory document model immediately; edits in Text View update the visual graph.
- **`XE-031`** · **Malformed Buffer Handling**: When the Text View buffer is not well-formed, Design View performs a **best-effort partial render** rather than clearing the canvas or blocking the view switch.
  - The parser recovers as far as it can and renders every structure it was able to resolve. Switching views is never blocked on well-formedness.
  - Regions that could not be parsed are shown as explicit gap markers on the canvas, positioned where the unparsed content sits in document order. Unparsed content is never silently omitted — an absence must be visible as an absence.
  - A persistent banner indicates that the graph is partial and names the parse failure, with navigation to the offending location in Text View.
  - The recovered model is a **render-only projection**. It never replaces the authoritative document model, and the unparsed source text is retained verbatim for serialisation.
  - **Editing While Partial**: Successfully parsed subtrees remain fully editable. Gap markers and any structure whose boundaries could not be resolved are read-only, and reject edit operations with an explanation rather than failing silently.
    - The canvas must visually distinguish editable regions from locked ones, so the user can tell what is safe to work on without attempting an edit to find out.
    - **Document-scope operations are blocked entirely while the buffer is malformed.** Extract Global ComplexType (§2.3) writes a new type definition under the root schema, and renaming a global type (§2.3) rewrites references across the whole file — neither can be performed safely when the document's global scope has not been fully parsed, regardless of whether the originating subtree parsed cleanly.
    - Insertions adjacent to a gap marker are rejected, since the correct document-order position cannot be determined.
- **`XE-032`** · **Responsiveness**: Parsing, validation, and serialisation must not block user input. The UI must remain interactive throughout, with a rendering target of 60 fps during canvas interaction.

#### 2.2.1 Rendering Type Derivation by Extension

Derivation by extension is the dominant structural pattern in the corpus — roughly 2,000 `xs:extension` declarations inside as many `xs:complexContent` blocks, covering about two in five of its complexTypes — so inherited content must be visible on the canvas rather than hidden behind the Details Pane.

- An expanded ComplexType box displays a **`Base Type | <baseTypeName>`** row in its header, mirroring the `Type` row on element cards.
- The base type renders as **its own encloser box nested inside** the derived type's box, labelled **`<baseTypeName> (extension base)`**, positioned first within the derived box.
- The base box owns its own model-group joint circle and child element cards.
- The derived type's own children hang from a **second, separate joint circle**, positioned after the base box. This ordering reflects XSD semantics, in which extension content appends after base content.
- Rendering recurses where the base type is itself derived by extension, producing nested `(extension base)` boxes to arbitrary depth.

#### 2.2.2 Rendering SimpleType Derivation

- Expanding an element whose type is a SimpleType or built-in primitive renders that type's **derivation chain** as a horizontal series of nodes, linked by plain connectors. No joint circle is drawn, as no model group is involved.
- The chain runs from the named SimpleType through each intermediate restriction base to the terminating built-in primitive (e.g. `UUID` → `ext:UniversallyUniqueIdentifierType` → `xs:string`).
- Each node in the chain carries its own expand/collapse control, allowing the chain to be revealed one link at a time.
- **`XE-033`** · **Facets are not drawn on the canvas.** Selecting any node in the chain loads its facets into the Details Pane (§2.4).
- **`XE-034`** · **Visual Type Language**: ComplexTypes render as rectangular encloser boxes; SimpleTypes and primitives render as rounded, pill-shaped nodes with a distinct type glyph. The two must be distinguishable at a glance.
- **`XE-082`** · **Optional Element Depiction**: An element whose effective `minOccurs` is `0` renders with a **dashed outline** on its card, and the **branch connector linking it to its parent model group's joint circle is dashed** along its whole length. An element with an effective `minOccurs` of `1` or more renders with a solid outline and a solid connector.
  - **The two marks are redundant with each other by design.** The card outline reads when the element is looked at directly; the dashed branch reads when scanning a model group's children as a set, where the connector is what the eye follows. Either alone would be legible in only one of those two ways of looking.
  - **This is the only depiction of optionality, not a second one.** The Cardinality Annotation (§2.2) is suppressed for `0..1` precisely because this rule covers it: line style carries the lower bound, and the label is reserved for elements that can repeat. The two never state the same fact twice — where the label does appear, on a repeating element that is also optional, it states the full range including the `0` and agrees with the dashed rendering.
  - **The rule is driven by the element's own effective `minOccurs`, and nothing else.** Enclosing group semantics do not change it: a child of an `xs:choice` is drawn dashed only if its own `minOccurs` is `0`, even though at most one branch of the choice is taken. Inferring optionality from the enclosing group would make the same declaration render differently depending on where it sits, which is exactly what a structural cue must not do.
  - **Effective, not written.** `minOccurs` is defaulted and therefore often absent from the source (§4, Implicit Defaults Rule); the render uses the effective value, so an element with no `minOccurs` attribute is solid.
  - The same rule applies to a **model group** whose own `minOccurs` is `0`: its joint circle and the stem leading into it are dashed, and its children follow their own values independently.
  - **Selection remains legible on a dashed card.** Selection thickens the outline (§2.2, Selection Does Not Re-root) without making it solid — a selected optional element is a thick dashed outline. Line style carries optionality, weight carries selection, and neither uses colour, so both survive greyscale, high-contrast modes, and both themes (§5, Theming).

### 2.3 Interactive Graph Manipulation & Canvas Actions

- **`XE-035`** · **Create Global Object**: Right-clicking **empty canvas space** in Design View offers creating a new global **ComplexType**, **SimpleType**, or **top-level Element**.
  - The user is prompted for a name, validated for uniqueness against the full resolved `include`/`import` closure (§2.1) on the same rule as Extract Global ComplexType (§2.3) — `xs:include` shares a target namespace, so a locally unique name can still collide across files. A collision is rejected inline and re-prompted.
  - The new object is written to the root schema of the active file and the **canvas re-roots onto it** (§2.2, Re-rooting), so the user is placed in the thing they just made rather than having to find it.
  - It is created empty: a ComplexType with no model group yet, a SimpleType with no base or facets yet, an Element with no type yet. Populating it uses the ordinary editing paths — an element with no type carries an unresolved reference until one is assigned (§2.2, Changing an Element's Type).
  - This is the counterpart to **Delete** below, and the only path to a global object that does not begin with existing structure. Extract Global ComplexType (§2.3) promotes structure that already exists; this creates from nothing.
- **`XE-036`** · **Drag & Drop**: Elements and model groups are repositioned by dragging them directly on the canvas. Two moves are supported, and they are the same gesture distinguished only by where the drop lands.
  - **Reorder within a group**: dropping between two siblings of the item's own parent model group moves it to that position. An insertion indicator shows where it will land before the drop is committed.
  - **Move to another type**: dropping onto a different type box moves the item out of its source group and into the target's model group. The move is a genuine relocation — the item is removed from the source.
  - **Dropping on a group rather than between siblings appends.** Where the drop lands on a model group or type box as a whole — anywhere in it that is not an insertion point between two existing children — the item is placed **last** among that group's children. Appending is the only position a whole-group drop can mean; an item that belongs somewhere else is then dragged into place, which is the reorder case above.
  - **The reachable set is what the canvas is already rendering.** A drop target must be an **expanded** box in the current render of the active tab. Drag and drop never re-roots, never expands anything, and never spans tabs. Moving something into a collapsed group means expanding that group first, as a separate deliberate act; moving it to a type that is not in the current render uses **Copy & Paste** (§2.3), which is also the way to *copy* rather than move — dragging has no copy variant, so the gesture has one meaning.
    - **Auto-scroll**: a target that is rendered but outside the viewport is reachable. Dragging toward a canvas edge scrolls the canvas in that direction, at a rate that increases with proximity to the edge, and stops when the pointer moves away or the drop is committed. This moves the viewport only; it changes neither the root nor any expansion state.
    - No spring-loading. Hovering a dragged item over a collapsed box does **not** expand it. Auto-expansion would put structure on screen that the user did not ask for, and would make where an item lands depend on how long the pointer lingered.
  - **Order is preserved as authored, whether or not it is significant.** Reordering is allowed inside `xs:choice` and `xs:all`, where child order carries no meaning in XSD, as well as inside `xs:sequence`, where it does. In the first case the edit changes only the document text; the editor does not prevent it, reorder it back, or warn, because the author's chosen reading order is worth keeping.
  - **Invalid drops are refused** rather than corrected, with the pointer showing a no-drop cue and no document change: dropping an item onto itself or into its own subtree; dropping onto a **collapsed** box, which shows no children and therefore offers no position; dropping into a SimpleType box; and dropping onto a recursion-bound `…` indicator (§2.2), which stands for structure that is not rendered.
  - **Dropping into a base type box** (§2.2.1) edits the base type itself, not the derived type being viewed, and so changes every type derived from it. This is accepted without a prompt or a report: the base type box is a real type rather than a read-only echo, and editing what is on screen is what the canvas is for.
  - A completed drag is one semantic operation and therefore **one undo entry** (§2.3, Undo/Redo); undoing restores both the original parent and the original position within it. An abandoned drag — released outside any valid target, or cancelled with `Esc` — writes nothing.
- **`XE-037`** · **Model Group Edits**: Support adding child elements, adding sequence/choice groups, and converting a model group between choice and sequence. Reachable from context menus on the parent ComplexType box, the joint circle icon, and local element cards.
- **`XE-038`** · **Copy & Paste**:
  - Copy elements or entire nested model groups, recursively including their children.
  - Paste copied items as children of a selected element or group.
  - **The clipboard spans tabs.** Content copied in one file may be pasted into any other open file.
  - Where a pasted element's type is not present in the destination's resolved `include`/`import` closure (§2.1) — which built-in datatypes always are (§2.1) — the paste still succeeds and the reference renders as unresolved per §2.1. The paste is never refused for a missing type.
  - **Pasting into a different file prompts to bring dependencies with it.** The editor computes the types the pasted subtree depends on, transitively, and offers to copy those the destination lacks.
    - Where a dependency name already exists in the destination, the user is prompted per name to **overwrite** the existing definition or **keep** it and let the pasted content reference it. Same-name types are not assumed to be the same type.
    - Declining the dependency copy leaves the references unresolved, which is a legitimate outcome — the author may intend to add an `import` instead.
    - The paste and any accompanying dependency copy are one semantic operation and therefore one undo entry (§2.3, Undo/Redo).
- **`XE-039`** · **Delete**: Support deleting an element, a model group (with its subtree), or a global type definition.
  - **Deleting a global type is permitted even where it is still referenced.** References to it become unresolved and render per §2.1 — red squiggly underline, Bottom Pane entry — rather than being rewritten or deleted alongside it. Deletion never edits a reference.
  - Before deleting a referenced type the editor reports how many references exist and in which files, so the user knows the size of what they are breaking. The report informs; it does not block.
  - This is deliberately asymmetric with **Rename** below, which does rewrite references. Renaming preserves the author's intent that the references keep pointing at the same type; deleting does not, and inventing a replacement target would be a guess.
- **`XE-040`** · **Rename**:
  - Renaming a global type updates the declaration and rewrites all `type=` and `base=` references **within the same file only**.
  - If the renamed type is also referenced by another currently open file, the editor warns the user, names the referencing file, and reports the reference count. It does **not** rewrite cross-file references. Cross-file coupling in the corpus is low but non-zero: 3 types are referenced across files at 31 sites.
- **`XE-041`** · **Edit Annotations**: Opens the annotation editor for the selected element, type, or enumeration value. Reached by **double-clicking a rendered annotation** on the canvas, and from **Edit Annotations** on the context menu of an element card, a type box, or an enumeration value (§2.4) — the context-menu route being the one that works when annotations are hidden or the object has none yet.
  - The editor is a **window listing every annotation on that object**, in document order, with the first one — the one the canvas renders (§2.2) — identified as such. Selecting an entry edits that annotation individually; the list is the mechanism by which annotations beyond the first are reachable at all.
  - Annotations may be **added, edited, deleted, and reordered** within the editor. Reordering matters because order decides which annotation the canvas shows.
  - `xs:documentation` attributes carried in the source, such as `xml:lang` and `source`, are displayed and preserved. Editing the text of an annotation never drops them.
  - Committing the editor is **one undo entry** (§2.3, Undo/Redo) covering every change made in it, and marks the tab dirty. Cancelling writes nothing.
- **`XE-042`** · **Right-Click Element Shortcuts**:
  - **Toggle Optional**: Toggles `minOccurs="0"`. When cleared, the `minOccurs` attribute is removed (1 is the implied default).
  - **Toggle Unbounded**: Toggles `maxOccurs="unbounded"`. Enabling it on an element that already carries a numeric `maxOccurs` **overwrites** that value. Disabling it returns the element to `maxOccurs` 1, which is the implied default and is therefore **removed from the document** rather than written explicitly; the Details Pane shows it as an unbolded `1`. The corpus contains a few hundred numeric `maxOccurs` values, so the overwrite path is reachable in practice; the original numeric value is recoverable only via undo.
  - **Set Numeric maxOccurs**: Bounded numeric occurrence values are entered through the Details Pane, not the context menu toggle.
  - **Edit Annotations**: Opens the annotation editor described above.
  - **Extract Global ComplexType**: Converts an element's inline anonymous complexType hierarchy into a globally defined `<xs:complexType>` under the root schema. The user is prompted for a name, defaulting to `<elementName>Type`, and the element's `type` attribute is rewritten to reference the new global type.
    - **This is a primary authoring path, not a repair tool.** The intended workflow is to mock up structure inline — adding elements, sequences, and choices directly under an element — and then extract that structure into a named global type once its shape has settled. It is required in R1 and is exercised by authoring, not by the reference corpus.
    - **Recursive Extraction**: Where the extracted subtree contains further nested anonymous complexTypes, all of them are promoted to named global types in a single operation.
      - **No type is ever created silently.** The user must explicitly confirm a name for every type the operation will create, including nested ones. There is no bulk-accept, no auto-naming, and no path that writes a type the user has not seen and approved.
      - Prompts are presented outermost-first, following the reading order of the canvas.
      - Sequential prompting is deliberate. A single consolidated dialog listing all pending names was considered and rejected; naming each type in canvas order keeps the user's attention on one type at a time. The accepted cost is that a deep extraction produces a corresponding number of prompts, and that cancelling late discards the naming work done so far.
      - The operation is **atomic**: cancelling at any point abandons the entire extraction and leaves the document unchanged. No partial promotion is written.
      - The whole extraction is a single semantic operation and therefore a single undo entry (§2.3, Undo/Redo).
    - **Naming and Collision**: Each name field is prefilled with `<elementName>Type` as a starting suggestion only; the prefill does not constitute confirmation. Names are validated for uniqueness against the **full resolved `include`/`import` closure**, not the active file alone, since `xs:include` shares a target namespace and a locally unique name can still collide across files. A collision is rejected inline and re-prompted, with the offending name retained in the field for editing. Extraction cannot proceed on a duplicate name.
    - The inverse operation (inlining a global type back to anonymous) is not required.
- **`XE-043`** · **Undo / Redo**:
  - Scope is **per tab**; each open file maintains one independent stack.
  - The stack is **unified across both views**. Design View operations and Text View edits share a single ordered history, and it survives switching views. An operation performed in one view can be undone from the other.
  - Granularity for Design View actions is **one entry per semantic operation**. A recursive Extract Global (§2.3) is a single entry regardless of how many types it creates.
  - Text View edits are not semantic operations and are **grouped by word boundary**: a run of typing forms a single undo entry, closed by a space, tab, or newline. Undo therefore reverses a word at a time rather than a character at a time.
    - Deletions group under the same rule, so a run of backspacing is reversed as one entry.
    - Discrete operations — paste, find-and-replace, block indent — always form their own entries and never merge into an adjacent typing run.
    - Boundary-based grouping is chosen over an idle-time interval deliberately: it is deterministic and therefore testable, whereas timer-based coalescing produces different results for the same input depending on typing speed.
  - **Undo/Redo Navigation**: Undo and redo return the user to the view and location where the affected edit was made. This is distinct from Navigation History (§2.2), which moves the user without changing the document; see that requirement for how the two interact. If an edit was made in Text View and the user has since switched to Design View, undoing that edit switches back to Text View and scrolls to the affected line; the same applies in reverse for Design View operations, which recentre the canvas on the affected node. An edit is never reversed off-screen or in a view the user cannot see.
    - Where consecutive undo entries belong to the same view, the view is not switched repeatedly — the switch occurs only when the target view differs from the active one.
  - No history is discarded on a view switch. The unified stack removes the invalidation problem that separate per-view histories would otherwise create, in which undoing in one view could reach a state inconsistent with edits made in the other.
  - Redo is cleared when a new operation is performed after an undo, per normal convention.

### 2.4 Panel Layout

- **`XE-044`** · **Menu Bar**: A conventional menu bar carries every action in the application, including those duplicated on the Top Ribbon. The ribbon is a shortcut to frequent actions; the menu is the complete surface, and platform menu conventions are followed on each OS.
  - **File menu**: **New** (§2.1, File Creation), **Open**, **Open Recent**, **Close**, **Save**, **Save All**, and **Exit**. Close, Save, and Save All act on tabs and follow the dirty-state prompts in §2.1, Save Model; **Save All** writes every dirty tab, and reports per file if any write fails rather than abandoning the rest.
  - **Tools menu**: actions that operate on the whole document or the whole schema rather than on the current selection — **Create Schema Subset…** (§2.1), **Unused Types Report** (§2.1), and **Format Document** (§4). The first two read the resolved closure and modify nothing, which is what separates them from the editing actions on the context menus. **Format Document is the exception**: it rewrites the active document's structural whitespace, dirties the tab, and takes an undo entry. It sits here rather than on a context menu because its scope is the whole document and it has no selection to act on.
  - **Open Recent**: A list of recently opened files, most recent first, each opening in a new tab. The list ends with **Clear Recent Files**.
    - Its length is a user preference (§2.4, Preferences), defaulting to **10**.
    - Entries show the file name, with the containing directory disambiguating files of the same name — a schema set commonly reuses names across directories.
    - An entry whose file no longer exists is not silently dropped: choosing it reports that the file is missing and removes it from the list then.
    - The list records paths only, and is kept whether or not **Re-open Files From Last Session** is enabled. The two are independent: one is a menu of history, the other is what opens at startup.
- **`XE-045`** · **Top Ribbon**: A persistent horizontal ribbon above the main view, carrying the quick actions that are reached often enough not to belong in a menu. It holds the **Text / Design view toggle** (§2.2), the **Navigation History** back and forward controls (§2.2), **Validate** (§3, Explicit user command), and the two **display toggles** below. Everything on the ribbon is also reachable from the menu bar and by keyboard; the ribbon is a shortcut, never the only path to an action.
  - **Show Element Types**: when off, element cards omit the `Type` row and show the element name alone. The type is unchanged in the document — this is a display setting, nothing more. While it is off the double-click-to-change-type path (§2.2) has no row to act on, so changing an element's type goes through the Details Pane instead.
  - **Show Annotations**: when on, `xs:annotation` / `xs:documentation` text is rendered inline on the canvas, on **both element cards and type boxes**. When off, an object carrying an annotation still shows a small indicator, so the user can tell "no documentation" from "documentation hidden" and reach the text in the Details Pane.
  - Both toggles affect **Design View rendering only**. They change no document content, produce no dirty state, and create no undo entry (§2.3) — a display toggle is not an edit. In Text View they are shown disabled rather than hidden, so the ribbon does not change shape between views.
  - Defaults: **Show Element Types on, Show Annotations off.** A type name is a short, structural fact and belongs on the card; documentation is prose of unbounded length and would set the width of every box that carries it. Both are one click from the ribbon, so a user who wants annotations always visible pays for that choice once.
- **`XE-046`** · **Preferences**: User preferences **persist across sessions**, restored at startup, and are application-wide rather than per file or per tab. The persisted set includes the two ribbon display toggles, the per-view font sizes and faces, the navigation highlight duration, the annotation row limit, the recent-files list length and the re-open setting below, the Light/Dark theme override (§5), the attribute serialisation order (§4), the formatting preferences (§4, `XE-085`), and the line ending policy (§4, `XE-086`).
  - **Font Size**: **Two settings, one per view** — a Text View size and a Design View size — since the views use different font families (§2.2, Text View). Each is the size its view opens at, and each view's font face is configurable alongside it.
    - **`Ctrl` + scroll wheel changes the size of the view it is used in**, on the platform-conventional modifier, and only that view. In Text View this scales the text as an editor's zoom does; in Design View it is the canvas zoom, since box geometry is derived from font metrics rather than set independently.
    - **`Ctrl` + scroll never writes the preference.** It is a working adjustment held for the session, on the same principle that navigation never writes an expansion marker (§2.2): the application always starts at the configured sizes, so a user who zoomed in to read something has not thereby changed what they see tomorrow. A reset action returns the active view to its configured size.
    - **Design View has no separate zoom level.** Boxes and cards are sized to the text they contain, so changing font size rescales the whole graph and reflows box widths — which in turn changes how much annotation text fits within the row limit (§2.2, Annotation Rendering). Nothing in the document changes; this is layout only.
    - The size is bounded at both ends so the canvas cannot be zoomed to illegibility or to a single box filling the viewport, and the current value is displayed while it is being changed.
  - **Navigation Highlight Duration**: How long the Text View landing highlight persists after a panel navigation (§2.4, Navigating to an Object), in milliseconds. The default is **1000**; 0 disables the highlight.
  - **Annotation Row Limit**: The maximum number of text rows an annotation occupies on the canvas (§2.2, Annotation Rendering). A whole number of at least 1; the default is 4. There is no unlimited setting — an unbounded annotation would defeat the purpose of the limit, and the full text is a hover away.
  - **Re-open Files From Last Session**: When on, the editor reopens the files that were open when it last closed. Only **file paths** are recorded; the editor restores which files are open and nothing else about the session. A recorded file that has since been moved or deleted is skipped and reported once, and never blocks the rest from opening. Unsaved changes are still lost on close, as §2.1's explicit-save model has no autosave and no journal — this reopens files, it does not restore work.
  - Preferences are stored in a per-user configuration file in the platform-conventional location for each supported OS, outside any schema directory. Nothing about a user's preferences is ever written into a schema file.
    - **The file is JSON**, read and written through a source-generated serialiser so it stays trim-safe under §5's packaging (`0002`). Comments and trailing commas are accepted on read, so the file remains hand-editable and can be checked into a team's own repository; [`preferences-example.json`](preferences-example.json) carries the shipped defaults with each key explained.
    - **Every key is optional and an absent key takes its default**, so a file setting one preference contains only that one, and a preference added in a later release does not invalidate an existing file. An unrecognised key is ignored with a warning rather than treated as an error.
    - The file carries a **schema version**, bumped only when a key changes meaning or is removed. A file from a newer version than the application understands is refused rather than half-applied; an older one is migrated on read.
  - A configuration file that is missing, unreadable, or unparsable is replaced by the defaults and reported once. The editor always starts.
  - Expansion state (§2.2), the canvas root, navigation history, undo history, and scroll position are **not** persisted, whether or not files are reopened. They are per-tab session state, and a reopened file opens exactly as a freshly opened one does — collapsed, with an empty canvas and an empty history. Which files are open is the only thing carried across a session boundary.
- **`XE-047`** · **Navigating to an Object**: The Left Panel object tree, the Dependencies Tree, and the Bottom Pane all navigate to an object, and they do it identically. **Double-click activates**; a single click selects the row for keyboard use and navigates nothing. The three panels differ in what they list, not in how they behave.
  - **The active view decides where the user lands.** With **Design View** active, navigation re-roots the canvas on the object (§2.2, Re-rooting). With **Text View** active, it scrolls to the object's declaration and places the caret there. Navigation never switches views: the user chose the view they are working in, and a panel click is not a request to leave it.
  - **The Text View landing is briefly highlighted** — the object's declaration is marked for a short interval and then fades, long enough to catch the eye in a 147,419-line file. The duration is a preference (§2.4), defaulting to **1000 ms**; setting it to 0 disables the highlight. The highlight is a transient display effect: it selects nothing, changes nothing, and is not part of the document.
  - **An object in another file opens that file, without prompting.** Where the target lives in an `include`d or `import`ed file (§2.1) that is not already open, the editor opens it in a new tab, focuses that tab, and completes the navigation there. The user asked to go to the object; being asked to confirm opening the file it lives in would be a question with one sensible answer.
    - An already-open file is focused rather than opened again.
    - This is the one path that opens a file the user did not name. It follows from the closure being the unit of work (§2.1): the panels list objects across the closure, so they must be able to reach the files those objects are in.
    - Where the object cannot be reached because its file is unresolvable (§2.1), the editor reports the missing file and leaves the current tab as it stands.
  - Each navigation pushes a **Navigation History** entry (§2.2) in whichever view it lands in.
- **`XE-048`** · **Left Panel — XSD Objects Tree**:
  - Groups: Elements (messages), ComplexTypes, SimpleTypes.
  - Search bar supporting wildcard filters (`*` for any string, `?` for any single character).
  - Double-clicking an entry navigates to that object, per **Navigating to an Object** above. The tree holds no persistent selection and marks no current item on the canvas; a single click selects a row within the list only.
  - Holds roughly 6,300 objects for the reference corpus and is subject to the virtualisation requirement in §5.
- **`XE-049`** · **Right Panel — Details Pane**:
  - The pane is **tabbed**. An **Attributes** tab is always present. An **Enumerations** tab appears in addition whenever the selected object is a SimpleType that either carries `xs:enumeration` values already or has been marked as an enumeration on the Attributes tab (below). No other tabs are required in R1, and the tab strip is hidden when only one tab exists.
  - View and edit type properties, base types (extensions), and annotations.
  - View and edit the file's target namespace and its prefix declarations (§2.1, Namespace Handling).
  - **Attributes tab.**
  - **Complete Attribute Display**: Every attribute applicable to the selected object is listed, including those absent from the source document because they hold their implied default. The R1 defaulted set is exactly three: `minOccurs` (default `1`), `maxOccurs` (default `1`), and `abstract` (default `false`). `nillable`, `form`, `block`, and `final` are deferred per §1 — the pane must be able to take additional defaulted attributes without redesign.
  - **Default-Value Styling**: An attribute displaying its implied default renders in the **standard text style** — no colour of its own, nothing muted. An attribute holding a non-default value renders **both its label and its value in bold**, marking it as explicitly specified rather than inherited from the default. Weight alone carries the distinction, so it survives greyscale, high-contrast modes, and both themes without a colour token to verify.
  - **Editing a Default**: Editing a default to a non-default value writes the attribute to the document and bolds the row. Returning it to the default value removes the attribute and returns the row to standard weight.
  - Display foreign-namespace attributes (e.g. `ext:version`) as **read-only** metadata rows. The corpus carries roughly 6,300 such attributes.
  - **Facet Editor** for SimpleTypes, supporting the full XSD 1.0 facet set: `length`, `minLength`, `maxLength`, `pattern`, `enumeration`, `whiteSpace`, `maxInclusive`, `maxExclusive`, `minInclusive`, `minExclusive`, `totalDigits`, `fractionDigits`.
    - The pane lists every facet applicable to the selected type's base, including those currently unset, which display an empty value.
    - Supports adding, deleting, and reordering facets.
    - **`enumeration` is edited on the Enumerations tab, not here.** The Attributes tab reports how many enumeration values the type carries and links to that tab. Enumeration is the one facet that is a list rather than a single value, and at nearly 8,000 values corpus-wide it needs room the facet list cannot give it.
    - **Selecting `enumeration` in the facet list is how an enumeration type is started.** A newly created SimpleType (§2.3, Create Global Object) has no values and would otherwise have no Enumerations tab to add the first one on. Selecting the facet **reveals the tab immediately, empty**, so the user can switch to it and begin adding. The tab shows an empty-state prompt rather than a blank list.
      - Selecting the facet **writes nothing to the document**. An `xs:enumeration` element appears only when the first value is added; a type left with the facet selected and no values added is unchanged on save. Clearing the selection while values exist is a deletion of those values and is confirmed as one.
      - The facet is selectable once the type has a **restriction base**, since `xs:enumeration` is only meaningful under one. Before a base is set the control explains that rather than being silently absent — the ordinary path is to create the type, set its base, then mark it an enumeration.
    - Corpus usage, in descending order: enumeration (nearly 8,000 values), pattern (144), length, maxLength, minLength, maxInclusive, minInclusive, whiteSpace, minExclusive. Only the pattern count is exact, because §4's character-reference rule is measured against it.
  - **Correction to prior revision**: `minValue` and `maxValue` were listed as facets in an earlier draft. They are not XSD facets and have been removed.
  - **Enumerations tab.** Lists the selected SimpleType's `xs:enumeration` values in document order, one per row.
    - A control strip at the top of the tab carries **Add**, **Delete**, and **Move Up** / **Move Down** for the current selection. Delete removes the selected values; Move Up and Move Down shift the selection one position, keeping a multiple selection together as a block.
    - **Add inserts after the selected value**, so a value can be placed where it belongs without adding it at the end and walking it up. With **nothing selected — or a multiple selection, whose last row is used — it appends to the end and scrolls the list to the end**, so the new row is visible in a list too long to fit the pane.
      - Either way the new row becomes the selection and opens for editing immediately, and is scrolled into view. Adding several values in sequence therefore walks down the list from the insertion point rather than jumping back to the end each time.
      - A new value is created empty. An empty enumeration value is legal XSD but rarely intended, so one left empty is reported as a warning (§3) rather than being discarded or blocked.
    - **Double-clicking a value edits it in place.** Editing commits on Enter or focus loss and is abandoned on `Esc`.
    - **Right-clicking a value offers Edit Annotations** for that value (§2.3). An `xs:enumeration` facet may carry its own `xs:annotation`, and in a code-list schema that documentation is often the only description of what the code means, so it must be editable where the values are.
    - Order is preserved as authored and is what reordering writes, on the same rule as Design View reordering (§2.3, Drag & Drop): enumeration order carries no meaning in XSD, but the author's chosen order is kept.
    - Each Add, Delete, Move, or value edit is **one undo entry** (§2.3), and a multiple-row Delete or Move is one entry rather than one per row.
    - The list is virtualised per §5; individual lists run to hundreds of values.
- **`XE-050`** · **Dependencies Tree Pane**:
  - Right-click any type to display a **reverse dependency tree**: what uses the selected object, expanded recursively until it reaches the top-level elements that ultimately carry it. It answers "if I change this, what is affected", which is the question the Design View canvas cannot answer, since the canvas only ever looks downward from its root.
  - **Root**: the selected object. **Children of a type**: every use of that type in the resolved `include`/`import` closure (§2.1) — both the **elements declared with it** (`type="T"`) and the **types derived from it** (`base="T"`). A base type therefore shows, side by side, the elements that use it and the types that extend it; those are its two kinds of dependant and both belong in the answer.
  - **Elements are listed in their own right, not folded into their owning type.** An element is where a type is actually used, and its name is usually what the user recognises, so collapsing elements into the types that contain them would remove the most identifiable step in the chain.
  - **An element node has exactly one child: the type it is declared in** — the type whose model group contains it. That single step is what carries the chain upward: the element's owner is itself a type, whose own dependants are then listed under it, and so the tree alternates element, owning type, element, owning type until it terminates.
    - A **global top-level element** has no owning type and is therefore a leaf. Every branch that terminates does so at a global element, at a type nothing uses, or at the recursion bound below.
  - **Icons distinguish the three kinds** — Element, ComplexType, SimpleType — since a branch mixes all three and the names alone do not say which is which.
  - **Recursion bound**: a branch stops where an object already appears in its own ancestry within the tree, marked in the same way as the canvas recursion indicator (§2.2) and naming the repeating object. Without it a recursive or mutually recursive type would expand forever, exactly as it would on the canvas.
  - Branches are **built on expansion rather than eagerly**. A widely used base type in the corpus reaches a large fraction of its several thousand types, and computing the whole closure to draw a collapsed tree would not meet the §5 performance target.
  - Double-clicking an entry navigates to that element or type, per **Navigating to an Object** above, so a dependency chain can be followed by successive double-clicks.
- **`XE-051`** · **Bottom Pane — Validation Messages**:
  - Lists validation errors and warnings. Double-clicking an entry navigates to the reported object, per **Navigating to an Object** above — re-rooting the canvas in Design View, scrolling to and highlighting the declaration in Text View.

## 3. Validation

- **`XE-052`** · **Scope**: Full **XSD 1.0 schema validity** checking, not merely well-formedness and type-reference resolution.
- **`XE-053`** · **No suppression rules.** Foreign-namespace attributes such as `ext:version` are legal under the XSD schema-for-schemas, which permits attributes from other namespaces on schema components via a `##other` wildcard. They validate cleanly without an import and require no special handling.
- **`XE-054`** · **Cross-file resolution**: Validation operates across the resolved `include`/`import` closure, not the active file alone.
- **`XE-055`** · **Triggers**: A validation pass runs on exactly three events:
  - **File load**, once the document and its `include`/`import` closure have been read.
  - **Save**, initiated after the file has been written to disk.
  - **Explicit user command**, available from the menu and from **Validate** on the Top Ribbon (§2.4).

  Validation is **not continuous**. No pass is triggered by editing, by switching views, or on a debounce timer.
- **`XE-056`** · **Continuous Reference Resolution Check**: Separately from the validation pass above, the editor **continuously checks type and base references against the set of names defined in the resolved closure** (§2.1), and marks those that resolve to nothing.
  - This is a **name lookup, not validation**. It answers only "does a type by this name exist", not whether the reference is legal where it appears, whether the derivation is sound, or whether the content model is valid. Those remain the full pass's job.
  - It is cheap enough to run on every edit precisely because it is that narrow: the set of defined names is already held for the type picker (§2.2) and the object tree (§2.4), and a lookup against it costs nothing next to a schema-validity pass over an 8.3 MB closure. Where the buffer is malformed (§2.2) the check covers the references the lexer can still reach.
  - It runs in **both views** and produces the ordinary unresolved-reference marker (§2.1) — the red squiggly underline on the reference text, in Text View and on Design View element cards alike. This is what catches a type name typed by hand in Text View, where there is no completion to prevent the mistake (§2.1, Directive Resolution).
  - The set of defined names is refreshed as the user adds, renames, or deletes a global type, so a reference stops being marked as soon as the type it names is created, and starts being marked as soon as that type is deleted (§2.3, Delete).
  - Its results are **never stale**, which is the difference the user must be able to see: unresolved-reference markers track the current buffer, while every other marker reflects the last completed validation pass (§3, Marker Currency). Bottom Pane entries from this check are shown as current rather than carrying the staleness indication that applies to pass results.
- **`XE-057`** · **Save Is Never Blocked**: A failing validation result does not prevent saving. The user may save a schema with any number of validation errors, and the editor does not prompt for confirmation on save. Validation reports; it does not gate.
- **`XE-058`** · **Pass Granularity**: Each pass covers the full resolved `include`/`import` closure. Incremental or subtree-scoped revalidation is not required, as the infrequent trigger set makes a full pass affordable even at the §5 performance target.
- **`XE-059`** · **Load-Time Behaviour**: The editor becomes interactive as soon as the document is parsed and rendered, without waiting for the load-time validation pass to complete. The file can be read, navigated, and edited while the pass runs.
  - A progress indicator is displayed for the duration of the pass, showing that validation is under way and that the Bottom Pane is not yet populated.
  - The indicator is required on load specifically, where the pass runs unprompted and its absence would otherwise be indistinguishable from a schema with no errors.
- **`XE-060`** · **Background Execution**: Validation runs asynchronously and must never block user input. Editing, navigation, view switching, and saving remain fully available while a pass is in flight. Results are published to the Bottom Pane and to inline markers when the pass completes.
- **`XE-061`** · **Superseded Passes**: If the document changes while a pass is running, that pass is cancelled or its results discarded. Stale results must never overwrite newer ones.
- **`XE-062`** · **Result Staleness Indication**: Because validation is trigger-driven rather than continuous, displayed results can be arbitrarily out of date relative to the current buffer. The Bottom Pane must indicate both when a pass is in flight and when displayed results predate subsequent edits.
- **`XE-063`** · **Marker Currency**: Text View inline validation markers (§2.2) reflect the most recent completed pass only. They do not update as the user types and are subject to the same staleness indication. The exception is the unresolved-reference marker, which comes from the continuous reference check above and is always current.
- **`XE-064`** · **Inline Marker Vocabulary**: Severity is conveyed by two distinct inline markers, applied in Text View and on Design View element cards alike:
  - **Errors** — red squiggly (wave) underline.
  - **Warnings** — amber dashed underline.

  The two differ in both stroke pattern and colour, so severity remains distinguishable without colour perception, independently satisfying §5's requirement that information not rely on colour alone. Both colours must meet contrast in Light and Dark themes.
- **`XE-065`** · **Cascade Suppression**: Where a single root cause produces many derived failures — most commonly an unresolvable `include` or `import` (§2.1) — the Bottom Pane reports the root cause once and summarises the dependent failures as a count, rather than listing an entry per affected reference. Inline markers still appear at every affected site. Without this rule, one missing file would fill the pane with cascading entries and bury unrelated errors.
- **`XE-066`** · **Unresolvable directives**: See §2.1.

## 4. Formatting & Serialisation

- **`XE-067`** · **Comment Preservation**: The serialiser must preserve original XML comments, whitespace formatting, namespace declarations, and unrecognised XML nodes.
- **`XE-068`** · **Foreign Attribute Preservation**: Attributes in non-XSD namespaces are preserved byte-for-byte on write.
- **`XE-069`** · **Character Reference Preservation**: Numeric character references (`&#x20;`, `&#x7E;`, `&#nn;`) and named entity references (`&amp;`, `&lt;`, `&quot;`) are preserved in their **original source form** on write. They are not resolved to literal characters and re-serialised.
  - This matters most in `xs:pattern` facets, where the escaped form is chosen deliberately for legibility — a literal space inside a character class such as `[a-zA-Z0-9&#x20;\-_]{1,20}` is invisible and easily corrupted. The reference corpus uses character references in **75 of its 144 patterns**.
  - Resolving and re-serialising would be semantically equivalent for a regex but would produce a large spurious diff and degrade the source's readability. Neither is acceptable.
  - Preservation applies wherever references occur, not only in patterns.
- **`XE-070`** · **Ampersand Leniency**: A preprocessor escapes **raw, unescaped** ampersands inside annotation and documentation fields to `&amp;` before parsing, preventing parser failures on non-conforming schemas.
  - The preprocessor must escape only ampersands that do not already begin a valid character or entity reference. An ampersand introducing `&#x20;`, `&#nn;`, `&amp;`, `&lt;`, `&gt;`, `&quot;`, or `&apos;` is left untouched.
  - Escaping these would produce `&amp;#x20;` and corrupt the content — a failure the reference corpus would exhibit immediately across 116 character references.
  - The rule is scoped to annotation and documentation text. It does not apply to `xs:pattern` values or other attribute content.
- **`XE-071`** · **Attribute Ordering**: XSD attributes are serialised in a **fixed order, configurable in Preferences**. The shipped default is `name`, `type`, `minOccurs`, `maxOccurs`; a user may reorder it, and the configured order then applies uniformly.
  - **The configured order is a partial one, and the rest of the rule must be stated or it is not implementable.** Three groups are written in this sequence: the attributes named in the configured order, in that order; then **every other XSD attribute** — `abstract`, `base`, `value`, and the schema-element attributes among them — keeping its relative source order; then **foreign-namespace attributes**, also keeping their relative source order.
    - `abstract` is the only one of these the question is live for. It is declared on types, so it never co-occurs with `type`, `minOccurs`, or `maxOccurs`; all 70 in the corpus are written `name`, `abstract`, `ext:version`, which is what the rule above produces. The others — `base` on a derivation, `value` on a facet — are the sole attribute on their element, so their position is not observable.
  - **Ordering is strict and overrides preservation.** It applies to every element written on save, not only to elements the editor has modified. Where the source order differs from the configured order, it is normalised. Attribute order is therefore the one aspect of the original formatting the editor deliberately does not preserve; comments, whitespace, character references, and foreign attributes are unaffected by this rule and continue to round-trip verbatim.
  - **The default matches the corpus, measured.** Across the corpus's primary schema file — 19,377 elements carrying two or more attributes — **every one already conforms**, and no element places an unlisted XSD attribute before a listed one. The commonest sequences are `name, type` (5,874), `name, ext:version` (5,464), `name, type, minOccurs` (4,931), and `name, type, minOccurs, maxOccurs` (1,695). The default is chosen to match, so adopting the editor on this corpus produces **no normalising diff at all**. The other two corpus files have not been measured.
  - **Consequence**: the first save of a file whose attribute order differs from the configured order produces a diff at every affected element. This is intended behaviour, and is the cost of a single canonical order. It does not arise on the reference corpus, which already conforms; a team adopting the editor on some *other* existing schema should expect one normalising commit, and is best served by making it a commit of its own rather than mixing it with a substantive change.
- **`XE-083`** · **Line Ending Preservation**: A file's existing line endings are preserved exactly on write, **CRLF and LF alike**. For text the editor did not touch this already follows from Comment Preservation above; this requirement extends it to the text the editor itself writes, which preservation alone does not cover.
  - **A line the editor inserts uses the ending the file already predominantly uses**, so an edit never converts a file or leaves it mixed. Where a file's endings are *already* mixed, each is kept as authored — the editor does not normalise what it did not write.
  - **A newly created file** (§2.1, File Creation) uses the host platform's convention. It is the one case with no existing file to follow.
  - **The ending is detected per file, never per session and never per platform.** That detection is what `XE-086`'s policy preference selects *over*: under its default — Keep source file line endings — everything above holds unchanged, so the same schema edited on Windows and on Linux saves identically. That property is the reason keep is the default and the reason the corpus round-trip suite runs under it: otherwise a round-trip test passes on one CI runner and fails on another, and two authors on different platforms produce a whole-file diff between them. A user who chooses Use system convention has chosen to give that up, and gets the conversion only where `XE-086` says — on the lines the editor writes, and on the whole file when they explicitly run Format Document.
  - The reference corpus is **wholly CRLF** — every one of the 147,419 newlines in its largest file, with no bare LF anywhere in the three. It therefore gives the LF path no coverage at all, and purpose-built LF and mixed-ending fixtures are required (§6).

- **`XE-084`** · **Format Document**: A **Tools menu** command (§2.4) that reformats the active document to the configured formatting preferences below. It is the editor's only whole-document reformat; nothing else normalises formatting the user did not touch.
  - **Structural whitespace only.** Every element with element content starts and ends on its own line, indented one level per ancestor. The whitespace between elements is the formatter's to rewrite; nothing else is.
  - **An element with non-whitespace character-data content is not entered at all.** Its text is written back byte-for-byte, and **its closing tag follows the last character of that text wherever that falls** — on the same line when the text ends without trailing whitespace, on its own line when the text itself ends in a newline. Both forms occur in the reference corpus and they are not two styles: they are one rule applied to two values. A preference controlling this would corrupt the value, so there is none.
    - The consequence for editing is direct: documentation typed over five lines in the annotation editor (§2.3) with no trailing newline is saved with `</xs:documentation>` hard against the fifth line's last character, because that is what the value is.
  - Attribute values, `xs:pattern` facets, comments (`XE-067`), foreign attributes (`XE-068`) and character references (`XE-069`) are untouched. Attribute **order** is `XE-071`'s, unchanged by this command.
  - **Idempotent**: formatting an already-formatted document changes nothing. **Model-preserving**: parsing, formatting and re-parsing yields the same schema model.
  - It is a single undo entry (§2.3) and dirties the tab like any other edit.
- **`XE-085`** · **Formatting Preferences**: The formatting `XE-084` and `XE-087` produce is configurable, persisted with the rest of the preference set (§2.4). **The shipped defaults reproduce the reference corpus byte-for-byte**, measured across all three files.

  | Preference | Values | Default |
  | --- | --- | --- |
  | Indent character | tab or spaces | **tab** |
  | Spaces per level | 1–8; **available only when the indent character is spaces** | 4 |
  | Empty element form | `<tag/>`, `<tag />`, or `<tag></tag>` | **`<tag/>`** |
  | Attribute layout | all on the start-tag line, or one per line above a threshold | **all on the start-tag line** |
  | Attribute wrap threshold | 1–16; used only when the layout is one-per-line | 4 |
  | Final newline at end of file | on or off | **on** |

  - **There is no tab-width setting.** One tab is one level; how wide a tab *displays* is Text View's tab-stop concern (§2.2) and never the document's.
  - **Blank lines between declarations are always zero**, with no preference. The corpus has none — all 218 blank lines in its primary file fall inside `xs:documentation` text — and preserving stray ones would make `XE-084` non-idempotent for no benefit. Blank lines *inside* character data are untouched, like all other character data.
- **`XE-086`** · **Line Ending Policy**: A preference (§2.4) selecting between **Keep source file line endings** (the default) and **Use system convention**.
  - Under **keep**, `XE-083` applies exactly as written: the file's own ending is detected and used for every line the editor writes.
  - Under **system**, lines the editor writes use the host platform's convention, and **`XE-084` converts the whole file** to it. That is the only sanctioned whole-file ending conversion in the editor, and it is deliberately an explicit user action rather than something a save performs silently.
  - The default is keep because it is the setting under which a schema saves identically on every platform (`XE-083`), and the corpus round-trip suite runs under it.
- **`XE-087`** · **Formatted Insertion**: An object created in Design View (§2.3) is inserted at the correct position in the source text, rendered by **the same formatter `XE-084` uses, at the same preferences**, and **nothing outside the inserted span changes**.
  - Stated concretely, because this is the case the requirement exists for: inserting an element, type, or facet into a schema held entirely on one line produces a correctly indented, correctly line-broken new subtree, while every other byte of the file remains on that one line. The surrounding document is normalised only when the user runs `XE-084`.
  - The insertion's **indent depth comes from its position in the tree, not from the neighbouring text**, which may carry no indentation to imitate.
  - Its **line ending follows `XE-086`**, which under the default is the same rule `XE-083` applies to any inserted line.
- **`XE-072`** · **Implicit Defaults Rule**: Attributes holding their implied default value are never written to the document. This covers the three defaulted attributes in scope: `minOccurs` (`1`), `maxOccurs` (`1`), and `abstract` (`false`). The editor treats the default as the effective value for display and editing purposes (§2.4) while omitting it from serialised output.
  - **Round-trip note**: The corpus contains one explicit `minOccurs="1"`. Applying this rule removes it on save, producing a one-line diff against the original file. This is intended behaviour, not a defect. It is separate from, and smaller than, any diff produced by the strict ordering rule above.

## 5. Non-Functional & Quality Attributes

- **`XE-073`** · **Delivery Form**: A **desktop application**, installed and run locally on the user's own machine. Not a web application, not a browser-hosted tool, and not mobile. This is settled, and it is the primary input to the technology-stack decision rather than an outcome of it.
- **`XE-074`** · **Packaging**: Distributed as a **self-contained installable artifact per platform**. Installing or running the editor must not require the end user to obtain a runtime, SDK, interpreter, or package manager, nor to fetch anything over the network at install time or on first run. Whatever the application needs is inside the artifact.
  - Developer-side dependency management is unconstrained. Contributors may use whatever toolchain, package manager, and lockfile the chosen stack brings; the constraint applies to what reaches the end user.
  - A runtime may be **embedded** in the artifact, but never **required** of the user.
  - **How the artifact is assembled is unconstrained.** Static linking, dynamic linking against libraries shipped inside the artifact, and an embedded runtime are all equally acceptable. The requirement is that the end user acquires nothing, not that the binary is monolithic — "self-contained" describes what the user has to fetch, never how the parts are linked. Some licences, the LGPL among them, permit distribution under other terms only where the user can relink; that route stays open (`docs/decisions/0001-licensing.md`).
  - This is a constraint on the stack, not on the feature set: a stack that cannot produce a single self-contained installable for Windows, macOS, and Linux is disqualified, however well it suits the rest of the specification.
  - It also reinforces §2.1's offline posture. An editor that fetches dependencies on first run would not work in the environments this schema corpus lives in.
- **`XE-075`** · **No Network Egress**: The application makes **no outbound network requests**. No telemetry, no usage analytics, no crash or error reporting, no update check, and no fetching of fonts, icons, or other assets at runtime — every asset the editor needs is inside the artifact (§5, Packaging). The only files it reads are the ones the user opens and the `include`/`import` targets those reach on local disk (§2.1, Location Resolution, which excludes network URLs in R1).
  - This is a **constraint on the stack and its libraries**, in the same way packaging is. A framework or library that reports crashes, checks for updates, or loads assets remotely by default is either configured off with that proven, or not used.
  - The reason is the material: schema, element, and file names in a controlled interface standard are not neutral data, and a crash report carrying a stack trace and an open file path discloses more than the user agreed to. An editor for this corpus has to be safe to run on a disconnected machine and provably quiet on a connected one.
- **`XE-081`** · **Supply-Chain and Code Security**: The editor ships with **no dependency carrying a known unfixed vulnerability**, and with **no unresolved Critical or High static-analysis finding** in its own code. Two different checks, because they catch different things: composition scanning over the dependency tree for published CVEs, and static analysis — SonarQube or equivalent, named once the stack is chosen — over the code the project writes.
  - **Both run in the build**, not as a periodic audit. A Critical or High finding, from either tool, blocks the merge; Medium and Low are recorded and triaged rather than gating.
  - **A dependency with a known CVE is not adopted.** Where one is disclosed against a dependency already in use, the response is to update, replace, or — if neither is possible — record an explicit justification and mitigation alongside the stack decision (`docs/decisions/`). What is not acceptable is an unrecorded exception.
  - **Packaging (§5) raises the stakes rather than lowering them.** Every dependency is inside the installed artifact, and the application fetches nothing at runtime (§5, No Network Egress), so a vulnerable library ships with the product and stays on the user's machine until they install a new build. There is no server-side patch path and no silent update; the check therefore has to happen before release, because afterwards is expensive.
  - Prefer a **small dependency surface** for the same reason: on this delivery model every library added is a library to be watched for the life of the product.
- **`XE-076`** · **Performance Target**: The editor must open, render, edit, and save schemas of at least **10 MB** without perceptible lag or UI freezes. The reference corpus main file is 8.3 MB / 147,419 lines, giving roughly 20% headroom against this target.
- **`XE-077`** · **Virtualisation**: Rendering must be virtualised wherever collection size scales with schema size — specifically the Text View line list, the left panel object tree (~6,250 entries), and the Details Pane enumeration editor (individual lists run to hundreds of values; nearly 8,000 enumeration values corpus-wide). Enumeration lists are uncapped.
- **`XE-078`** · **Selective Rendering**: Design View renders only the expanded subtree beneath the current canvas root (§2.2), not the full schema graph. Because expansion state is per object and therefore shared across occurrences (§2.2, Expansion State), a single re-root can bring a large subtree into view at once; the render must stay within the §5 performance target when it does.
- **`XE-079`** · **Theming**: Full Light and Dark mode support with a user override toggle, persisted with the other preferences (§2.4). All surfaces — text editor, canvas, backgrounds, and input controls — update immediately on change.
- **`XE-080`** · **Accessibility (a11y)**:
  - Colour contrast conforming to WCAG 2.1 AA.
  - Visible keyboard focus indicators on all fields and controls.
  - Keyboard shortcut navigation for common workspace operations.

### Verification gaps

These are not decisions but coverage notes for test planning. Four R1 requirements cannot be verified against the reference corpus, because the corpus contains no instance of what they handle:

| Requirement | Section | Corpus coverage |
|---|---|---|
| Extract Global ComplexType | §2.3 | 0 anonymous complexTypes |
| Create Global Object | §2.3 | authoring path, not a corpus feature |
| Ampersand preprocessor (escape path) | §4 | 0 raw ampersands |
| Unresolvable directive handling | §2.1 | all references resolve |
| Line endings, LF and mixed (`XE-083`, `XE-086`) | §4 | 0 bare LF — the corpus is wholly CRLF |
| Formatting variance (`XE-084`, `XE-085`, `XE-087`) | §4 | none — the corpus is uniformly one-tab-per-level CRLF, with `<tag/>` and no `<tag></tag>` |

Each needs purpose-built test fixtures. The line-ending row is easy to overlook, because the corpus exercises the CRLF path so thoroughly that a serialiser hard-coding CRLF would pass every corpus test while being wrong.

The formatting row is the same trap one level up: the corpus is the formatter's *default-output* fixture and gives no coverage of any non-default setting or malformed input. Its fixtures are built rather than found — space-indented, `<tag />`, a whole schema on a single line, a multi-line documentation value ending **without** trailing whitespace, and one ending **with** it. The single-line file is the acceptance test for `XE-087`, and the two documentation values are the acceptance tests for `XE-084`'s character-data exclusion.

Character reference preservation (§4) is the opposite case — heavily exercised, with character references in 75 of the corpus's 144 patterns.
